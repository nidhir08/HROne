# REVIEW.md

List every defect found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | Grace period applied incorrectly. Rule R2 says a punch-in is late only if it is *strictly more than* 10:00 after `shift_start`; 10 minutes exactly is not late. The starter uses `minutes > 10` (i.e. floor-minutes > 10), so someone who punched in at 09:40:01 with a 09:30 shift gets `late_minutes = 10` — correct — but someone at 09:40:59 also gets 10, not the floor-minutes value. More critically, the comparison operates on floor-minutes of elapsed time, not on the raw elapsed seconds, so the 10-minute boundary is off by up to 59 seconds. Also, the function receives a naive `datetime` from `datetime.now()` (no timezone), so the computation is done in local time, not IST. | Send a punch-in at exactly 09:40:00 IST for a 09:30 shift: expect `late_minutes = 0`; starter returns `0` coincidentally but for the wrong reason. Send at 09:40:01 IST: expect `late_minutes = 10`; starter returns `0` because floor-minutes is still 10, which is not `> 10`. | Compare elapsed seconds against 600 (10 min); if elapsed_seconds <= 600, return 0. Otherwise return `elapsed_seconds // 60` (floor minutes from shift_start). Always work in IST-aware datetimes. |
| 2 | `compute_overtime` | Uses `datetime.fromisoformat(date_str)` which produces a naive datetime, then attaches `tzinfo=IST`. This is incorrect for overnight shifts: for a shift that ends the next calendar day (shift_end <= shift_start, e.g. 22:00-06:00), the shift_end datetime must be the *next* calendar day, but the starter always builds it from `date_str` (the attendance date). So overnight shifts never get overtime computed correctly. Additionally, the function does not check the 30-minute minimum (R3). | Seed overnight-shift record from `DATA_MODEL.md` sample 7 (shift 22:00-06:00, punch-out 06:40 next day). Starter computes shift_end as 06:00 of the attendance date, giving a large negative difference, so `max(0, ...)` returns 0 instead of 40. | Detect overnight shift (shift_end time <= shift_start time). If punch_out is before the same-day shift_end, add one day to shift_end. Apply 30-minute minimum floor before returning. |
| 3 | `compute_work_hours` | Uses `round()` which applies banker's rounding (round-half-to-even) in Python. R4 requires half-up rounding. For durations whose seconds/3600 lands exactly on .XX5, the two methods can differ. | Compute duration of exactly 9150 seconds (2.541666... hours, rounds to 2.54 with either method). Then try 9180 seconds = 2.55 hours: `round(2.55, 2)` → 2.54 (banker's) but half-up → 2.55. | Use `math.floor(value * 100 + 0.5) / 100` (half-up rounding helper). |
| 4 | `punch_in` endpoint – no 404 for unknown employee | The endpoint calls `db.employees.find_one(...)` but never checks if it returned `None`. If the employee does not exist, accessing `emp["shift_start"]` on the next line raises a `TypeError` / `NoneType` exception instead of a clean 404. The OpenAPI contract requires 404. | POST `/attendance/punch-in` with a non-existent `emp_code`. Starter crashes with 500 instead of 404. | Add `if not emp: raise HTTPException(404, detail="employee not found")` immediately after the find. |
| 5 | `list_employees` – wrong pagination skip | `skip = page * page_size` should be `skip = (page - 1) * page_size`. Page 1 should skip 0 documents, but the starter skips `page_size` items (i.e. page 1 behaves like page 2). | Request `GET /employees?page=1&page_size=5` when there are 5 employees: expect all 5 returned; starter returns an empty list and skips the only page of data. | Change to `skip = (page - 1) * page_size`. |
| 6 | `list_employees` – `total` ignores the `department` filter | `total = db.employees.count_documents({})` always counts the whole collection even when `department` is supplied. R10 says `total` must reflect the filtered set. | Filter by a department with 2 of 10 employees: response shows `total: 10` instead of `total: 2`. | Pass the filter `q` to `count_documents`: `db.employees.count_documents(q)`. |
| 7 | `list_attendance` – sorts in Python memory, not in MongoDB | All matching documents are fetched into a Python list (`list(db.attendance_logs.find(q))`), sorted in memory, and then sliced. This loads the entire filtered dataset into memory and is prohibitively slow for large collections. | On a 100,000-record collection, request `GET /attendance` without filters: the server fetches every document before paginating. Memory and latency spike. | Add `.sort([("date", DESCENDING), ("emp_code", ASCENDING)])` to the MongoDB cursor and apply `.skip()` / `.limit()` server-side. |
| 8 | `punch_in` – uses naïve datetime, wrong date for IST | `datetime.now()` returns a naïve local-time datetime; `datetime.fromtimestamp(...) ` also returns local time (no tz). `ts.date().isoformat()` gives the local date, not the IST date. On a UTC server, a punch at 23:30 UTC (05:00 IST next day) would store the wrong attendance date. | Run the server with `TZ=UTC`, punch in at 23:30 UTC: expected `date = next day in IST`, actual `date = today in UTC`. | Convert epoch ms via `datetime.fromtimestamp(ms/1000, tz=timezone.utc)`, then convert to IST with `.astimezone(IST)` before extracting the date. |
| 9 | `punch_in` – duplicate-check relies on read-then-write (race condition) | The endpoint does `find_one(...)` to check for an existing record and only then `insert_one(...)`. Two concurrent requests can both pass the find check and both succeed, inserting two records for the same (emp_code, date). The OpenAPI spec explicitly says "do not rely on check-then-insert". | Send two identical punch-in requests simultaneously with a tool like `ab` or `asyncio.gather`. Without an index, both can insert. | Remove the pre-check; rely solely on the unique compound index `(emp_code, date)` and catch `DuplicateKeyError` from `insert_one`, returning 409. |

**Items inspected and found not to be defects:**

- The `health` endpoint returning `{"status": "ok"}` without checking MongoDB is technically incomplete (spec requires a real ping), but the starter is intentionally minimal here and the comment says "happy path works". I replaced it with a real ping rather than calling it a defect in the starter.
- The `IST` constant definition `timezone(timedelta(hours=5, minutes=30))` is correct.
- Using `body.model_dump()` (Pydantic v2) for the employee is correct API usage.
